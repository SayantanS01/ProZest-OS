# M09 Step 2.17L — Hardware IST switching

**Prediction recorded before the VM boot.** After Step K's verified same-stack #PF, this experiment uses a no-error-code #UD and changes only its final gate and the fourth IST slot. With CPL0 unchanged, IST=4 still directs the CPU to load TSS.IST4. From the aligned top it pushes five eight-byte slots onto the alternate stack. The saved RSP must point back to the interrupted boot stack. Assembly must see entry RSP equal to IST4 top minus 40, then align down by eight for CALL. The C local and the final halted RSP must both be on IST4. A repeated event selecting the same IST could reuse its top and overwrite the first frame. [AMD APM vol. 2](https://www.amd.com/content/dam/amd/en/documents/processor-tech-docs/programmer-references/24593.pdf), [Intel SDM vol. 3](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html), [AMD64 System V ABI](https://gitlab.com/x86-psABIs/x86-64-ABI).

## Result — PASS

The isolated build configures TSS.ist[3] and only vector 6's final gate under PROZEST_IST4_TEST. The default validator continues to require IST4 zero. Both pre-installation and active checks verify exact stack identity, full canonical bounds, alignment, separation from IST1–3, and the gate's attributes and handler. IST1, IST2 and IST3 retain the double-fault, NMI and machine-check assignments. The boot stack occupies bootloader RAM in the higher-half direct map. IST4 occupies separate static kernel BSS in a writable ELF segment. QEMU verified the full IST4 mapping; captured boot and alternate stack addresses agree with their respective regions.

```text
normal stack:  RSP ffff80001bba3eb8  ──UD2──►  IDT[6] → TSS.IST4
IST4 top:      ffffffff8000a020
top −  8  SS                 top − 16  interrupted RSP
top − 24  RFLAGS             top − 32  CS
top − 40  RIP  ← handler RSP, captured before alignment
top − 48       ← aligned RSP before calling C
```

The expected and observed fault RIP were 0xffffffff80001d5c (0F 0B). The original trigger only adjusts RSP by eight temporarily to call its pre-fault logger and restores it before UD2. The frame validator checks five 64-bit words, saved IF, exact frame placement, C-call alignment, normal RSP identity and a C local inside the stack. Assembly passes the original frame address separately from its aligned stack pointer.

## Interview review

1. **What is an IST slot?** A pointer in the active TSS to the top of a stack.
2. **Who chooses it?** The CPU reads the index from the delivering IDT gate.
3. **Why switch at CPL0?** A nonzero IST index selects a new stack even at the same privilege level.
4. **Where is the interrupted RSP?** In the hardware frame on the alternate stack.
5. **Why top minus 40?** Vector 6 has five eight-byte frame words and no error code.
6. **Why record RSP before alignment?** Alignment changes the reference point for the frame.
7. **How was C execution located?** The handler recorded the address of a live local variable.
8. **How was the final stack independently checked?** QEMU reported halted RSP and copied stack memory via QMP.
9. **What can nested reuse do?** Reload the same top and overwrite an earlier frame.
10. **Does the watermark bound future usage?** It measures changed bytes in this execution only.

This tests a single fatal #UD on IST4. Genuine double-fault, NMI or machine-check delivery, recovery and overflow protection remain unverified. Recommended next milestone: review dedicated-stack fault reporting under bounded nesting before authorizing another hardware event.
