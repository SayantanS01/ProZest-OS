# M09 Step 2.17K — Genuine page-fault delivery

**2026-11-24 · PASS on one QEMU/KVM CPU.** Step J verified a five-word frame for invalid opcode. This experiment verified the additional hardware error-code slot for vector 14, independently comparing the data address in CR2 with the instruction address in the saved frame.

## Why this read was safe to test

The target 0x0000008000000000 is canonical in four-level mode. It begins the 512 GiB region selected by PML4 slot 1. The running kernel checked PAE and LA57, used the active CR3, checked the physical width reported by CPUID.80000008 and removed the low 12 control bits. The complete 4096-byte root page had to lie in bootloader-reclaimable RAM described by Limine. The experiment used the revision-six higher-half direct mapping with aligned offset and checked addition before reading one entry. A clear present bit rules out every mapping in that region, including lower-level large pages. A present root entry or an unverified root stops the experiment. No lower-level tables need to be dereferenced and the experiment issues no page-table writes.

Paging remained active with CR0=0x80010011, CR3=0x1e6ee000, CR4=0x20. The faulting instruction was MOV (%RAX),%RAX, bytes 48 8B 00 at 0xffffffff80001d7b. The pre-fault reporter returned the verified target in RAX. The caller restored its measured RSP before issuing the load. The processor saved the faulting instruction address and delivered through the active vector-14 gate with IST zero. [AMD system programming manual](https://www.amd.com/content/dam/amd/en/documents/processor-tech-docs/programmer-references/24593.pdf) and [Intel system programming manual](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

## Frame at the entry stack pointer

```text
offset   #PF                      #UD
 0       hardware error code      RIP
 8       RIP                      CS
16       CS                       RFLAGS
24       RFLAGS                   RSP
32       RSP                      SS
40       SS                       end
```

The first vector-14 stub instruction copies CR2 into RCX. RSI retains the original RSP, EDI supplies the vector number, and RDX records RSP after alignment for the C call. The dispatcher receives the error word from entry offset zero. Optional bits PK, shadow stack, SGX and AMD RMP are reported as raw indications. A zero bit does not establish support for a feature. CR4.PKE, PKS and CET were clear. The full raw-code equality check rejects any unexpected set bit.

## Interview review

1. **What does CR2 identify?** The virtual address whose access failed.
2. **What does saved RIP identify?** The instruction attempting that access.
3. **Why check canonicality?** A malformed address can raise a different exception before translation.
4. **How did the kernel prove absence?** The first translation entry had its present bit clear.
5. **Could a large page override that result?** No lower-level entry can be reached through an absent root entry.
6. **Why capture CR2 immediately?** Another page fault can replace it.
7. **Why is a zero error code meaningful?** It describes a supervisor data read with a non-present translation.
8. **How is vector 14 different from vector 6?** The CPU adds an error word below the saved RIP.
9. **Why keep two stack pointers?** One locates the untouched frame and the other meets the C ABI alignment rule. Their values happened to coincide in this run.
10. **Does the halt demonstrate recovery?** It demonstrates fatal reporting. Returning or repairing a mapping requires a separate design.

Only one same-privilege non-present read was exercised. Protection violations, writes, instruction-fetch faults, IST delivery and recovery remain unverified. Recommended next milestone: review a distinct IST stack-delivery test with pre-entry and handler-stack bounds before authorizing any injection.
